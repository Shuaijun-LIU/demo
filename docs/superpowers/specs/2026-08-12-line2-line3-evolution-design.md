# 多机械臂 Demo Line2 场景升级与 Line3 原生 MuJoCo 演进设计

**日期：** 2026-08-12

**状态：** 已完成方案讨论，等待书面规格复核

**基线：** `2026-08-12-multi-arm-investor-demo-design.md` 与已发布的 Line1 六场景

**机械臂：** Franka Panda；Demo 01/03/06 为三臂，Demo 02/04/05 为四臂

## 1. 目标与边界

本轮保留当前 Line1，不覆盖其六套 MJCF、视觉目录、截图或既有 URL；在同一个静态 Web 应用中增加默认展示的 Line2，并为六个主题分别搭建更克制、更真实且能直接承接连续协作任务的场景。Line2 不是静态布景换皮：所有物料、工具、工位和机械臂角色都必须服务于可演示的任务图、业务异常、恢复动作与终态验收。

同时，为 Line3 编写原生 MuJoCo 任务路线。Line3 运行于当前设备，不以浏览器为约束，目标是形成具备接触、传感器、工具切换、随机复位、成功判定和数据接口的可复用 simulation 任务。本轮对 Line3 只落盘规划，不实现仿真代码。

本轮不改变以下基线决策：

- 六个主题、Franka Panda 选型和三/四臂数量；
- 共享运行时、共享协调原语和静态 GitHub Pages 部署；
- 默认演示无需后端、API Key、在线模型或 GPU；
- Line1 可随时切回并保持原有外观与行为，便于版本对照。

## 2. 版本与导航架构

应用引入 `LineId = "line1" | "line2"`，顶部提供明确的 `Line 1 / Line 2` 切换器。Line2 为默认入口；场景选择仍为 Demo 01–06。URL 采用查询参数保存状态，例如：

```text
/demo/?line=line2&scene=demo05
```

刷新、复制链接和浏览器前进/后退均恢复相同 Line 与场景。参数缺失时进入 `line2/demo01`；无效值回退到默认值并保留可用页面。Line1 继续读取现有 `public/scenarios/demo01` 至 `demo06`，Line2 读取 `public/scenarios/line2/demo01` 至 `demo06`，避免同名文件互相覆盖。

建议的代码边界为：

```text
src/
  app/
    App.tsx                    # URL 状态、Line/场景选择和共享布局
    LineSelector.tsx           # Line1/Line2 切换
    SceneViewport.tsx          # 共享画布与 MuJoCo 场景加载
    RealisticAssetLayer.tsx    # Line2 GLB 视觉层、懒加载与代理降级
  scenarios/
    visualCatalog.ts           # 保留 Line1 数据
    line2Catalog.ts            # Line2 六场景、角色、任务提示和资源绑定
    assetRegistry.ts           # canonical object ID、来源、许可、视觉/碰撞映射
public/
  scenarios/                   # Line1 原样保留
  scenarios/line2/demo01..06/  # Line2 独立 MJCF
  assets/line2/                # 优化后的公开视觉资产
  assets/line2/ASSET_PROVENANCE.md
  licenses/                    # 第三方许可文本与归属说明
```

`SceneViewport` 接收 `lineId` 与 `sceneId`，根据目录选择 MJCF。Line2 的真实外观由 React Three Fiber 的 GLB 实例层呈现；MuJoCo 使用独立的简化碰撞几何和关节约束。二者通过 canonical object ID 绑定同一 `ScenarioSnapshot` 位姿，确保视觉物体能被抓取、交接、检测和分流，不成为与任务无关的装饰。

## 3. Line2 视觉语言

### 3.1 调色板

Line2 从高亮赛博蓝转为低饱和工业控制室风格。色值作为 CSS token 固定：

| Token | 色值 | 用途 |
|---|---:|---|
| `--l2-bg` | `#11161A` | 页面与 3D 远景 |
| `--l2-panel` | `#192126` | 面板、顶栏、悬浮卡片 |
| `--l2-panel-raised` | `#222B30` | 选中项和二级表面 |
| `--l2-steel` | `#56636A` | 框架、机械设备、边框 |
| `--l2-work-surface` | `#3F4B50` | 桌面与夹具 |
| `--l2-primary` | `#668A8A` | 克制的灰青主色 |
| `--l2-arm-1` | `#6E8792` | Arm 1 灰蓝 |
| `--l2-arm-2` | `#7A6E80` | Arm 2 灰紫 |
| `--l2-arm-3` | `#9A8257` | Arm 3 赭黄 |
| `--l2-arm-4` | `#607C78` | Arm 4 灰绿 |
| `--l2-success` | `#66816E` | 通过/完成 |
| `--l2-warning` | `#9A8257` | 待复核/恢复中 |
| `--l2-fault` | `#9B5F56` | 业务异常与 NG |
| `--l2-text` | `#D3D7D8` | 主文字 |
| `--l2-muted` | `#8E999D` | 次要文字 |

大面积 UI、桌体、料盘、工具和环境光不得使用发光材质；大面积青蓝径向光、霓虹描边和蓝色雾效从 Line2 移除。只有直径较小的设备状态灯可以使用微弱 emission，强度不超过 `0.03`，故障灯同样保持克制。场景照明采用中性主光、柔和暖补光和环境阴影，突出资产材质而不是彩色氛围光。

### 3.2 工业真实感规则

- Franka 保留白色/深灰原厂外观，角色差异用基座铭牌、末端环或 UI 泳道表示，不给整条机械臂染荧光色。
- 桌体使用粉末喷涂钢架、灰色台面、真实厚度和支脚；挡板、输送线、料架和安全围栏有明确支撑结构。
- 小物体优先采用有法线、粗糙度和可识别轮廓的 GLB；标签只用于演示识别，不遮盖主体材质。
- 夹具、相机、扫码器、秤、工具坞和回收箱必须处在机械臂可达空间内，并与任务流方向一致。
- 每个场景提供默认全景和至少一个关键动作近景；镜头不穿模，不以极端广角掩盖布局问题。

## 4. Line2 任务闭环通用结构

每个 Line2 场景必须声明并可视化以下内容：

1. 明确的初态：对象数量、位置、工具、夹爪与安全姿态；
2. 连续任务节点：每条臂何时取物、保持、交接、检测、加工或包装；
3. 至少一个真正的协作原语：`Handoff`、`Barrier`、`HoldWhile` 或 `ZoneLock`；
4. 恰好一次观众可见的 `ScriptedBusinessFault`；
5. 由任务图指定的恢复动作，而不是直接跳到成功；
6. 逐对象终态、库存守恒、工具归位和各臂 safe pose；
7. 禁用任一臂时无法满足强耦合谓词或超出路演节拍。

视觉预览阶段可以使用确定性关键帧，但对象的抓取、持有和释放必须更新 canonical custody；任务运行时接通后，UI、3D 资产层、计数和 oracle 读取同一快照。

## 5. Line2 六场景设计

### 5.1 Demo 01：精密电子检测、功能测试与上料

**机械臂与工位：** 三台 Panda 围绕 ESD 工作台。Arm 1 面向混料盘与条码相机，Arm 2 位于翻转/双面视觉夹具，Arm 3 位于功能测试座、A/B 上料盘和 NG 盒。可见对象包括电池/元器件包装、PCB 或测试板、周转盘、检测相机、测试探针和可换工具坞。

**连续任务：**

1. Arm 1 从混料盘取 P1，扫码完成 SKU 初分，进入共享交接区；
2. Arm 1 保持，Arm 2 闭合并确认，完成正式 `Handoff` 后 Arm 1 释放；
3. Arm 2 在翻转夹具完成正反面检测，将合格件放入测试缓冲位；
4. Arm 3 从工具坞取得或显式启用测试探针，执行功能测试；
5. Arm 3 将合格件送往 A/B 上料盘，外观或功能不合格件送往 NG；
6. P2–P5 以流水方式重叠执行，Arm 1 准备下一件时 Arm 2/3 继续当前工序。

**故障与恢复：** P3 缺少背面标记。Arm 2 检出后生成外观失败证据，将 P3 绕过功能测试并交给 Arm 3 分流至 NG。恢复不是重新判合格，而是保持生产线继续处理 P4/P5。

**验收：** P1→A1、P2→B1、P3→NG、P4→B2、P5→A2；探针回坞，库存守恒，三臂回 safe pose。禁用 Arm 1/2/3 任一角色都缺失必要工序或超过 90 秒。

**优先资产：** RoboTwin `061_battery`、`104_board`、`008_tray`、`024_scanner`；必要时以程序化测试夹具补充，避免引入来源不明的工业零件。

### 5.2 Demo 02：汽车低压线束强协作布线

**机械臂与工位：** 四台 Panda 分布在倾斜布线板四侧。板上有 S0/S1 连接器座、C1–C3 卡扣、B1 分支和张力可视化。线束使用有厚度的样条视觉体，控制点与连接器、夹爪和卡扣状态绑定。

**连续任务：**

1. Arm 1 插入并保持起始连接器 S0；
2. Arm 2 抓住中段，Arm 3 抓住末端；三臂在 `Barrier` 后同时建立 start/middle/end 三个 anchor；
3. Arm 2 随动维持张力，Arm 3 沿定位柱将末端送入 S1；
4. Arm 4 使用压扣工具依次锁止 C1、C2、C3，并处理 B1 分支；
5. 三个 anchor 在 Arm 4 压扣期间持续满足 `HoldWhile`，终检通过后按末端、中段、起始顺序释放。

**故障与恢复：** C2 首次只进入半锁止状态。Arm 4 的到位检测显示失败，退回安全高度、重新对准并二次压紧；其他三臂在此期间继续保持，不允许线束瞬移到成功状态。

**验收：** S0/S1 锁定，C1–C3 与 B1 全部闭合，目标曲线 RMS 误差≤25 mm，归一化张力处于 `[0.25, 0.75]`，所有夹爪释放且四臂归位。禁用 Arm 1–3 会破坏三锚点条件，禁用 Arm 4 无法完成卡扣闭合。

**优先资产：** 程序化线束与布线板保证可控拓扑；连接器/卡扣优先从许可清晰的 NIST 制造任务板 CAD 或自建简化几何获得。外部 CAD 在许可确认前只列入 Line3 候选，不进入公开站点。

### 5.3 Demo 03：食品多规格装盒、封签与称重

**机械臂与工位：** 三台 Panda 沿 U 形食品包装线分布。Arm 1 对应食品供料和订单缓存；Arm 2 对应蓝/黄平板纸盒库与开盒夹具；Arm 3 对应装填、封签、电子秤、合格出料和 NG 滑道。

**连续任务：**

1. Arm 1 按订单将 A/B 食品放到装填缓存位；
2. Arm 2 选择对应蓝/黄纸盒，在开盒夹具中成型并持续保持；
3. Arm 2 与 Arm 3 到位后触发 `Barrier`；Arm 3 在 `HoldWhile` 条件下装入食品；
4. Arm 3 关闭盒盖、贴封签并放到电子秤；
5. 重量和日期标签通过后出料，否则进入 NG；三臂同时准备下一订单。

**故障与恢复：** K3 外侧日期标签缺失。视觉检查在称重后拒收，Arm 3 将 K3 放入 NG；生产线继续 K4/K5，避免把缺陷件伪装成返工合格。

**验收：** K1(A)→Blue-1、K2(B)→Yellow-1、K3→NG、K4(B)→Yellow-2、K5(A)→Blue-2，产品与盒数守恒，三臂归位；禁用 Arm 2 使纸盒保持谓词失败，禁用 Arm 1 或 3 超过 90 秒或缺失工序。

**优先资产：** RoboTwin `bread`/`baguette`/`103_fruit`、`037_box`/`038_milk-box`/`113_coffee-box`、`008_tray`、`072_electronicscale`；纸盒标签使用项目自制纹理。

### 5.4 Demo 04：大型构件定位、紧固与质量扫描

**机械臂与工位：** 四台 Panda 围绕中央装配夹具。主梁和连接板具有明确孔位与基准面；Arm 3 一侧布置电动螺丝刀/探针工具坞，Arm 4 配有支撑垫和扫描相机。这里的“大型”指多臂相对尺度和持续保持关系，不声称 Panda 承载真实重型工业梁。

**连续任务：**

1. Arm 1 搬运主梁到夹具并持续保持；
2. Arm 2 将连接板对准基准面，Arm 4 从侧后方提供支撑；
3. 三臂达到姿态后通过 `Barrier`，中央装配体建立 multi-anchor；
4. Arm 3 在工具坞取得电动螺丝刀/低能量演示头，完成 F1；
5. Arm 3 执行 F2，Arm 4 同时扫描接缝和到位状态；
6. F1/F2 与接缝全部通过后，夹具接管 custody，各臂解除保持并回收工具。

**故障与恢复：** F2 首次到位开关失败。Arm 3 撤回、重新对准并补作业，Arm 4 复检；Arm 1/2/4 在恢复期间保持各自谓词，任何一臂丢失支撑都进入阻塞暂停。

**验收：** 连接板相对主梁 `90°±3°`，基准误差≤15 mm，F1/F2 安装、接缝扫描通过，夹具接管构件，工具归坞，四臂 safe pose。禁用任一臂都会破坏保持、支撑或工具工序。

**优先资产：** RoboTwin `032_screwdriver`、`030_drill`、`020_hammer`、`104_board`、`108_block`、`042_wooden_box`；支架、紧固孔、螺栓和工具快换器使用项目自建低面数模型。锤子仅作为工具架可识别物，不替代 F1/F2 的受控紧固头。

### 5.5 Demo 05：智能药房双处方纠错与包装

**机械臂与工位：** 恢复为原剧本的四台 Panda。Arm 1 面向 A 区药架，Arm 2 面向 B/C 区药架，Arm 3 面向双订单汇合盘、扫码器、计数区和退回箱，Arm 4 面向包装盒、封签位和取药窗口。布局必须让包装位与未复核药品物理隔离。

**连续任务：**

1. Arm 1 为 RX-01/RX-02 从 A 区拣选，Arm 2 同时从 B/C 区拣选；
2. 两条拣选流进入各自汇合盘，使用 `ZoneLock` 避免订单混盘；
3. Arm 3 对每件药盒扫码、计数并与处方集合比较；
4. RX-02 出现错误 B3 时，Arm 3 将其移至 return bin，并向 Arm 2 发出补拣 B1 的恢复节点；
5. Arm 2 补取 B1，Arm 3 复扫后将 RX-02 标记为 PASS；
6. Arm 4 只对 PASS 订单获得包装区锁，装盒、封签并送到取药窗口。

**故障与恢复：** 固定种子 `RX-20260812` 下，RX-02 应为 `{A2×1, B1×1, C1×1}`，Arm 2 首次误取 B3。错药必须由 Arm 3 识别并隔离，Arm 2 真实补拣，Arm 4 在 PASS 前不可开始包装。

**验收：** RX-01 仅含 `{A1×1, B2×1}`，RX-02 仅含 `{A2×1, B1×1, C1×1}`，B3 位于 return bin；五件正确药、一个错误盒、库存余量和事件满足守恒，两个处方包封签完成，四臂归位。禁用任一拣选、复核或包装角色均导致终态或 90 秒 SLA 失败。

**优先资产：** RoboTwin `080_pillbottle`、`037_box`、`008_tray`、`024_scanner`；项目自制 A/B/C 药盒标签、空盒标识、处方周转盘、扫码灯和封签器。所有药品明确标注为模型空盒，不模拟真实处方建议。

### 5.6 Demo 06：岭南果品分选、去核与复作业

**机械臂与工位：** 三台 Panda 沿果品进料、去核夹具和成品包装构成流水线。Arm 1 使用软指或柔性夹持外观，从浅盘取果并旋转检查；Arm 2 使用去核头和定向夹具；Arm 3 复核开口、装入透明成品盘并管理待熟/NG/果核箱。

**连续任务：**

1. Arm 1 依次取 G1–G6，在视觉位旋转检查并执行初分；
2. 合格果经正式 `Handoff` 交给 Arm 2，Arm 2 在夹具内定向并执行低力去核；
3. Arm 3 取出去核果，检查开口和果核去除状态；
4. 通过件放入四格成品盘，G2 进入待熟区，G4 进入表面缺陷 NG，果核进入 pit bin；
5. 三臂流水重叠处理下一果品。

**故障与恢复：** G5 首次去核后仍检测到果核。Arm 3 将其送入 rework 位，Arm 2 二次执行短行程，Arm 3 再检并装盘；G2/G4 属于正常品质分类，不计入业务故障次数。

**验收：** G1/G3/G5/G6 在四格成品盘且 `pitRemoved=true`，四枚果核在 pit bin，G2→unripe，G4→NG，工具和夹具复位，三臂归位。禁用分选、去核或复核任一角色均超过 100 秒或无法满足终态。

**优先资产：** RoboTwin `035_apple`、`103_fruit`、`008_tray`、`basket`；项目自建软指、透明成品盘、去核夹具、可拆果核和复作位。

## 6. 工具、末端与资产契约

### 6.1 可见工具体系

Line2 至少呈现以下语义工具：

| 工具 | 场景 | 任务作用 |
|---|---|---|
| 平行夹爪 | 全部 | 刚体取放、交接和保持 |
| 真空/食品适配吸具 | Demo 03 | 纸盒或轻量包装抓取 |
| 翻转夹具与测试探针 | Demo 01 | 双面检测与功能测试 |
| 压扣头 | Demo 02 | C1–C3 锁止与二次压紧 |
| 电动螺丝刀/检测探头 | Demo 04 | F1/F2 作业和到位验证 |
| 扫码器与封签器 | Demo 05 | 药盒识别、处方门控和包装 |
| 软指与去核头 | Demo 06 | 易损果品抓取、去核与复作 |

工具坞必须显示占用状态。视觉阶段允许通过显式启用/停靠动作表达换工具；Line3 才实现完整的工具体关节、接触与连接约束。任务图只依赖 `ToolAdapter` 的语义 ID，不依赖网格文件名。

### 6.2 资产注册表

每个公开资产在 `assetRegistry.ts` 和 `ASSET_PROVENANCE.md` 中记录：

- canonical object ID 与场景实例；
- 原始来源、原始相对路径或 URL、作者/组织、许可；
- 是否修改、优化方法和导出日期；
- visual GLB、碰撞代理和物理参数；
- 文件大小、纹理分辨率与 attribution 文本。

资产实例必须能映射到任务对象；纯背景装饰另行标为 `set-dressing`，不得出现在库存或成功 oracle 中。

## 8. Line3：原生 MuJoCo 可复用任务规划

Line3 的目标不是把 Web 关键帧搬进 Python，而是将六个主题升级为可复位、可度量、可生成轨迹和可接入策略的原生 MuJoCo 环境。建议根目录为 `simulation/line3/`，每个任务拥有独立 MJCF、资产、配置、oracle 和测试。

### 8.1 统一环境接口

```python
obs, info = env.reset(seed=seed, options=options)
step = env.step(action)
success = env.oracle(snapshot)
state = env.get_state()
env.set_state(state)
```

观察至少包含各臂关节/末端、夹爪与工具状态、对象位姿、接触、任务阶段、共享区锁和相关传感器；动作支持每臂关节位置或末端增量控制，并预留策略级离散技能。`get_state/set_state` 必须覆盖 MuJoCo 状态、任务图、PRNG、custody、工具、故障和计时器，保证同种子确定性重放。

### 8.2 物理与任务真实性梯度

| Demo | Line3 重点物理 | 关键传感器/判定 | 随机化 |
|---|---|---|---|
| 01 | 刚体夹持、翻转夹具、探针接触 | 双面标记、探针接触/功能结果 | 混料盘姿态、SKU、缺陷件 |
| 02 | 多点线缆或分段柔性体、连接器插入、卡扣 | 插入力、卡扣到位、张力/路径误差 | 线束初形、卡扣摩擦、C2 故障 |
| 03 | 食品/纸盒接触、盒体保持、称重 | 盒内包含物、重量、标签 | 订单、尺寸、质量和标签缺陷 |
| 04 | 多锚点构件、导向插入、紧固工具接触 | 位姿误差、F1/F2 力/到位、接缝扫描 | 构件初姿、孔位、F2 故障 |
| 05 | 小盒抓取、汇合盘、包装门控 | 条码、计数、库存与包装状态 | 处方、货位、固定一次错拣 |
| 06 | 软接触近似、果核可拆约束、去核行程 | 外观等级、果核约束、开口检查 | 果形/尺寸/成熟度、G5 复作 |

对柔性线束和果品软体采用分级实现：先用稳定的分段刚体/约束模型建立可复现任务，再以计算代价和接触稳定性为依据升级模型，不把高保真软体作为第一可运行版本的门槛。

### 8.3 资产工程

Line3 对每个视觉资产建立独立碰撞资产：凸分解或手工 primitive、合理惯量、质量、摩擦和接触组。CAD/GLB 进入 MJCF 前完成坐标、单位、法线、网格闭合和质量检查。转换记录必须包含源文件哈希、比例、重心、碰撞近似和许可。

资产优先级为：

1. 已确认许可的本地 RoboTwin/Menagerie 资产；
2. 项目自建夹具、线束、卡扣、工具坞和包装结构；
3. 许可核验后的 NIST CAD 或 CC BY 资产；
4. 只在本机使用且不可再分发的资产，放入忽略目录并由下载脚本或说明恢复。

### 8.4 任务可复用性与数据接口

每个任务提供：

- 固定演示种子和训练/评估种子范围；
- 参数化 reset、对象扰动和故障注入；
- 逐阶段奖励与独立的布尔成功 oracle，成功不得仅由奖励阈值推断；
- 专家状态机或关键帧轨迹，输出动作、观测、接触和事件 trace；
- 单臂禁用、多臂同步和恢复分支的基准；
- headless smoke test、确定性测试、库存/状态守恒测试和短视频渲染脚本；
- 可对接 Gymnasium 风格 wrapper、离线数据集导出和后续 RoboTwin/ManiSkill 风格策略接口的稳定语义字段。

Line3 详细实施计划需逐场景列出 MJCF 文件、资产来源、物理参数、控制器、任务阶段、传感器、故障、oracle、测试、预计性能和验收视频，不以一句“参考 benchmark”替代落地路径。

## 9. 错误处理

- URL 或 Line 参数错误：回退到 Line2/Demo01，并保持应用可操作；
- MJCF 加载失败：显示 line/scene/file 信息与重试按钮，不继续播放；
- GLB 加载失败：保留同位姿代理、显示资产级错误，任务逻辑仍可检查；
- WebGL/WASM 不可用：显示兼容性说明，不呈现虚假 READY；
- 对象视觉位姿与快照不一致：开发模式立即报错，演示模式暂停并回滚当前节点；
- 许可或来源不完整：构建时拒绝将该资产复制到公开包；
- Pages 构建：每次 `main` 推送执行 `npm ci`、测试、构建、上传与部署，部署失败不得被页面截图掩盖。

## 10. 测试与验收

### 10.1 目录与交互

- Line1 与 Line2 各有 6 个可选择场景，共 12 个组合；
- URL 查询参数可直达、刷新和分享；错误参数安全回退；
- 切换 Line 或场景会停止旧运动、释放资源并复位新场景；
- Line1 视觉回归不受 Line2 CSS token 和目录影响；
- Demo05 Line2 明确渲染四台 Panda 和四条角色泳道。

### 10.2 场景与任务准备度

每个 Line2 场景都必须通过场景契约测试，覆盖臂数、角色、对象 ID、工具、协作原语、故障恢复边、终态 oracle、库存守恒、safe pose 和禁臂反事实。视觉检查必须证明：机械臂基座竖直、桌面水平、工具和物体可达、工序流向清晰、故障恢复位置真实存在。

在完整 TaskRuntime 接通前，界面必须把状态如实标成“场景与任务路径预览”，不得用 `READY/已完成` 暗示完整动作闭环已经实现。TaskRuntime 接通后才升级为“可运行 Demo”。

### 10.3 视觉与性能

- Line2 不出现现有霓虹青背景、强蓝雾、大面积发光边框或荧光角色色；
- 六场景均保存统一分辨率全景截图，Demo02/04/05 另存协作近景；
- Chrome 桌面端无资源 404、控制台未处理异常或相机穿模；
- 首次进入单场景满足资产预算，场景切换不持续增长 GPU/JS 资源；
- 生产构建使用相对 base，可由 GitHub Pages 子路径直接访问。

### 10.4 完成定义

Line2 场景阶段完成需同时满足：

1. 六套独立 MJCF 与真实感视觉资产已搭建；
2. 六套场景的物体、工具和位置均与本规范任务链对应；
3. Line1/Line2 与六场景切换可用，分享链接正确；
4. 调色板、资产许可、大小和加载降级符合规范；
5. 单元、契约、构建、浏览器冒烟与截图检查通过；
6. GitHub Actions Pages 部署成功，公开链接可加载资源；
7. `simulation/line3/` 的详细实施计划已写明六任务的资产与技术路径，但未把未实现的 Line3 标为完成。

## 11. 实施顺序

1. 固化版本路由、Line2 token、资产注册与许可清单；
2. 复制并优化少量代表性资产，验证 GLB 视觉层和 MJCF 代理同位姿绑定；
